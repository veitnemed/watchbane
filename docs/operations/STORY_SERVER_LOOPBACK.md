# Watchbane: локальная проверка отдельного сервера поиска

Это лабораторный сервер, не публичный сервис или обновление Qt. Используйте отдельное окружение с `requirements-story-server.txt`, заранее проверенную папку официальной E5 и разрешённый оператором локальный TMDb JSONL. Ни модель, ни исходный каталог не поставляются или скачиваются сервером. Формат файла совпадает с [валидатором каталога](../architecture/STORY_STARTER_CATALOG.md); сервер индексирует только пригодные описания `ru-RU`. Типизированный формат ID сам по себе не доказывает происхождение данных: фактический источник и права на этот снимок подтверждает оператор.

```sh
python -m web.story_api --catalog /path/to/approved.jsonl --model-dir /path/to/verified-e5 --port 8765
```

Точка входа привязана к `127.0.0.1`, без журнала доступа. Не выставляйте её в сеть: в этом срезе нет аутентификации, TLS или разделения пользовательских лимитов. При старте проверяются контрольные суммы модели и каталог, затем строится один индекс в RAM. При ошибке старт не завершается. Приложение не открывает профиль Qt, не меняет коллекцию и не обращается к TMDb.

- `GET /healthz`: `{"ready": true}` после готовности индекса.
- `POST /v1/search`, `Content-Type: application/json`: поле `query` (1–600 символов) и необязательное `limit` (1–10, по умолчанию 5). Текст передаётся только в теле, не в URL.
- Ответ содержит `source: "tmdb"` и список `results`: типизированный `id`, тип фильма/сериала, название, год, русское описание, фрагмент в качестве подсказки и `language: "ru-RU"`. Результат не подтверждает каждое сюжетное условие.
- Ответы поиска, включая ошибки, помечены `Cache-Control: no-store`. Ошибки не возвращают тело или текст запроса. Один поиск на процесс; если он уже идёт, следующий получает `503 search_busy`. Для проверки приватности запускайте именно точку входа выше, не произвольный ASGI-конфиг с журналом доступа.

Для отдельного нагрузочного эксперимента можно задать `--local-rate-per-minute` (1–3600) и необязательно `--local-rate-burst` (1–60, по умолчанию меньшее из заданной частоты и 5). При выключенном флаге поведение не меняется. Доступный кредит расходуется на корректный запрос до проверки занятости: при пустом бюджете первым идёт 429 с `Retry-After` в секундах, иначе занятый сервер по-прежнему отвечает 503. Это общий бюджет процесса без идентификаторов пользователя или сохранения запросов; он не защищает публичный вход, не реализует распределённую квоту и не означает, что сервер можно выставлять наружу.

Локальные HTTP-контрактные тесты: `python -m pytest -q tests/test_story_api.py` с дополнительным тестовым пакетом `httpx`. Для измерений отдельно записывайте время до `healthz`, время ответов после готовности и пиковую RSS всего процесса; малый частный каталог не доказывает производительность публичной установки.

## Подготовка очереди TMDb Daily ID Exports

`web.tmdb_ids.plan_daily_ids` принимает два локальных gzip-файла одного дня с именами из [официальных Daily ID Exports](https://developer.themoviedb.org/docs/daily-id-exports). Он строит ограниченный детерминированный список пар «тип, ID», пропускает строки с явной взрослой меткой или с неизвестным значением, а также выдаёт манифест с SHA-256 обоих архивов и очереди. Файлы проверяются целиком, даже если лимит выборки уже набран. Смена источника, даты или лимита требует нового контрольного состояния. Хеши связывают точные байты, но не устанавливают их происхождение или право использования.

Экспорт не содержит описаний; выборка ID не равна каталогизированным тайтлам. Создание очереди не обращается к TMDb, не гидратирует метаданные и не сохраняет прогресс. Доступ к Detail API, проверки происхождения, покрытия и правил хранения остаются отдельными этапами. Синтетические gzip в тестах не подтверждают фактическое покрытие источника.

`web.tmdb_hydration.hydrate_id_plan` принимает эту очередь, отдельный SQLite-файл и явный ограниченный транспорт. Он фиксирует конечный результат на каждый типизированный ID; при остановке на запасной локали незаконченный тайтл повторяется, уже зафиксированные пропускаются. `requested_locale` указывает локаль запроса, а не гарантированный язык текста: перед индексацией потребуется отдельная проверка. При HTTP 429 остановка без скрытого повтора; новый запуск с новым лимитом решает оператор. База не связана с пользовательским профилем и не поставляется пользователям. Пока проверено только через подставной HTTP-ответ, без живого вызова Detail API.

Если первый типизированный Detail (RU) вернул [документированный TMDb код 34](https://developer.themoviedb.org/docs/errors) вместе с HTTP 404 и проверенным JSON-ответом того же запроса, checkpoint фиксирует `unavailable` только для этого ID и этого плана. Возобновление внутри того же плана его пропускает, следующий снимок может проверить его снова. Существующий checkpoint обновляется одной транзакцией с сохранением прежних записей. Отчёт считает `unavailable` отдельно, экспорт не создаёт для таких ID карточек. Неопределённый 404, 404 после уже полученного RU-ответа, 429, ошибки авторизации, транспорта и разбора, исчерпание бюджета по-прежнему оставляют текущий ID на повтор.

Для первого **разрешённого** живого микропрогона создайте отдельный план с `per_media_limit=1` и новым checkpoint. До отправки убедитесь, что очередь содержит один фильм и один сериал: из-за фильтра допуска исходный файл может не дать пригодных ID. С лимитом до четырёх попыток хватает по два локальных запроса на тайтл (RU и при необходимости EN), если не требуется остановка по ошибке. Лимит не переопределяет ответы 429. По окончании различайте запланированные, проверенные, недоступные и записи с пригодными синопсисами по типу; запрошенная локаль сама по себе не устанавливает язык текста.

Текущая очередь ограничена 5 000 ID на тип и сначала проходит фильмы. Это максимум 10 000 входных ID, а не гарантированный выход в 10 000 пригодных описаний. Для роста нужны согласованные непересекающиеся выборки с раздельными контрольными состояниями или явное исключение уже проверенных ID: увеличение лимита нарушает исходный манифест и не продолжает тот же checkpoint. Пока такого расширения на живых данных не проверяли.

Для непересекающихся порций заранее зафиксируйте одно число групп (2–256). Вызов `plan_daily_ids(..., cohort=IdCohort(count=8, index=0))` выбирает одну группу; следующие индексы 1…7 используют те же два исходных снимка и отдельные checkpoints. Ключ включает тип и ID, манифест закрепляет индекс группы, их число и схему разбиения. Пустые группы также имеют разные манифесты. Обычный план без `cohort` не меняется, но его выборка может пересекаться с новыми группами; не считать её ещё одной непересекающейся группой. Лимит на тип остаётся внутри каждой группы, поэтому все группы вместе не гарантируют полный каталог. Это опция офлайн-планировщика, не запуск импорта и не подтверждение прав на данные.

## Ограниченный запуск на Linux

Для первого лабораторного замера можно ограничить процесс двумя **доступными** логическими CPU через `taskset` и виртуальное адресное пространство через `ulimit -v`. Например, для процесса, которому уже доступны CPU 0 и 1:

```sh
( ulimit -v 12582912
  taskset -c 0,1 python -m web.story_api --catalog /path/to/approved.jsonl --model-dir /path/to/verified-e5
)
```

Лимит 12 ГиБ относится к адресному пространству, не равен измеренному потреблению RAM и не моделирует процессор Oracle A1. На проверочном Linux x86-64 процессе в таких границах 50 описаний и локальная FP32 E5 дали готовность примерно за 8,2–8,8 с и пиковую RSS около 1,42 ГиБ. Одна серия из шести одновременно отправленных запросов дала один ответ 200 и пять явных `503 search_busy`; это проверка отказа при нагрузке, не поддержка шести одновременно работающих запросов.

[Oracle Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm) документирует для бесплатного Ampere A1 Flex месячные лимиты 1500 OCPU·ч и 9000 ГБ·ч, а также ограничения региона, доступности и изъятия простаивающих ресурсов. Не переносить квоты платного плана и не включать платный аккаунт ради проверки. [ONNX Runtime](https://onnxruntime.ai/docs/get-started/with-python.html) предоставляет CPU-пакет для Linux ARM64; совместимость всей сборки Watchbane и производительность на A1 ещё не проверены. В окружении разработки нет PostgreSQL/pgvector; готовность такого индекса и публичного хостинга не проверены. Сначала необходимы отдельный индекс, разрешённая база, HTTPS и ограничение нагрузки, безопасная конфигурация и проверка развёртывания.

## Проверка пути Qt без локальной модели

Когда сервер готов, запустите Watchbane с переменной `WATCHBANE_EXPERIMENTAL_STORY_PORT`, равной тому же порту TCP. В Qt введите сюжет и выберите «Поиск на тестовом сервере…». Подтвердите передачу текста отдельному локальному процессу. По Enter и без подтверждения запрос на сервер не отправляется. Можно отменить ожидание или отдельно запустить обычный локальный поиск. Отмена не возвращает уже отправленный текст. Для этого среза нужен отдельно запущенный лабораторный сервер; это не пользовательская конфигурация публичного онлайн-поиска. Сетевые постеры у серверных результатов не запрашиваются. Для отдельного эксперимента включите `--artwork-metadata` на тестовом сервере и `WATCHBANE_EXPERIMENTAL_STORY_ARTWORK=1` в Qt. После обычного согласия тот же запрос может получить относительные пути TMDb. Qt показывает только совпавшее уже закэшированное превью, не скачивает картинку, не меняет кэш и не сохраняет путь в коллекцию. На чистом профиле, при отсутствии файла или при недопустимом размере остаётся заглушка. Без этих флагов поведение не меняется; включённый клиент требует подтверждения версии от сервера и не повторяет запрос сам.

В экспериментальном клиенте можно явно показать объём **этого** индекса: `--index-metadata` на сервере плюс `WATCHBANE_EXPERIMENTAL_STORY_INDEX=1` в Qt. С согласия пользователя тот же POST получает поле `index` только при подтверждении заголовка `Watchbane-Search-Index: 1` обеими сторонами. Числа отражают загруженные пригодные описания по типам после отбора, а не количество строк исходного файла, результатов запроса, просмотренных тайтлов или всей базы TMDb. С этим режимом дополнительных запросов нет; без флагов контракт прежний.

### Проверка вариантов индекса

`--cache-dir /path/to/private-cache` явно включает кэш только матрицы каталога на диске сервера. Указать отдельную непубличную директорию оператора; папка профиля клиента не используется. При старте всё равно проверяются файлы модели. При несовпадении хешей, изменённом каталоге или повреждённой матрице кэш пересобирается; запросы и их векторы не записываются. Старые поколения пока удаляет оператор.

`--prepared-index` включает отдельную лабораторную реализацию с предварительно подготовленными плотными векторами и инвертированными символьными индексами без второго лексического индекса. Полный скан матрицы сохраняется, это не ANN. На 50 реальных тестовых тайтлах в паре запусков ответы полностью совпали на 10 отдельных запросах; замер на таком размере не показал ускорения HTTP. По умолчанию оставлен прежний алгоритм.

### Офлайн-подготовка серверной матрицы

В существующей закрытой директории оператора на локальном POSIX-диске можно заранее построить матрицу для разрешённого снимка и уже проверенных весов FP32. Утилита не запускает HTTP и не скачивает ничего; старый файл не заменяется.

```sh
python -m tools.qa.prebuild_story_passages \
  --catalog /path/to/approved.jsonl --catalog-sha256 EXPECTED_SHA256 \
  --model-dir /path/to/verified-e5 --cache-dir /path/to/private-cache \
  --startup-passage-batch-size 4
```

Используйте тот же каталог, каталог кэша, модель и размер пакета при запуске сервера. SHA матрицы в кратком отчёте связывает проверенные байты, но не даёт права на их распространение. Файловая система должна поддерживать жёсткие ссылки. При неизвестных правах на каталог кэша, изменении входного файла во время сборки, подменённой ссылке или повреждённой существующей матрице утилита отказывает; не ремонтируйте занятый кэш на месте, выберите новую закрытую директорию. У пользователя ничего не скачивается и не устанавливается.

Для обновления офлайн-матрицы можно передать сразу четыре дополнительных аргумента: `--previous-catalog`, `--previous-catalog-sha256`, `--previous-cache-dir` и `--previous-snapshot-sha256`. Старый снимок и матрица проверяются заново; при несовпадении новый файл не строится тихо с нуля. Используются только векторы с тем же типизированным ID и точным текстом при той же модели и размере пакета. Старый файл остаётся неизменным; новый публикуется без перезаписи. Инкрементальный и полный расчёт могут отличаться на иной платформе, поэтому строгий запуск принимает SHA именно выбранной проверенной матрицы.

Для строгого запуска добавьте к команде сервера `--expected-catalog-sha256 <SHA каталога>` и `--expected-snapshot-sha256 <SHA матрицы из отчёта>`. Используются оба аргумента и существующий `--cache-dir`; `--previous-catalog` нельзя сочетать с этим режимом. Если входные байты, модель, размер пакета или матрица не совпадают, сервер не становится готовым и не создаёт новую матрицу. По умолчанию остаётся прежний режим с возможностью пересборки.

### Первый ответ после повторного запуска (эксперимент)

На Linux x86-64, после подтверждённого чтения матрицы на 1 000 синтетических однопредложенческих описаниях, 546 из 579 мс первого ответа ушли на E5-кодирование пяти фрагментов. Полная сборка матрицы уже оставляет эти тексты в оперативном кэше модели; чтение матрицы не делает этого. Этот эффект не равен универсальному «разогреву» ONNX.

Лабораторный параметр сервера `--skip-singleton-evidence` не кодирует фрагмент повторно, если выбрать можно только одно предложение и дополнительное ранжирование выключено. На свежем повторном запуске того же синтетического эксперимента первый ответ занял 90 мс при том же полном JSON. Многопредложенческие описания по-прежнему сравниваются. Параметр выключен по умолчанию и не включается в Qt: он меняет состояние кэша и на пакетно-чувствительном кодировщике может изменить выбор фрагмента в последующем запросе. Совпадение на малом разрешённом каталоге и одном x86-64 окружении не доказывает точное равенство на всех моделях и платформах.

### Типизированное состояние ответа (эксперимент)

Обычный `POST /v1/search` по-прежнему возвращает ровно `source` и `results`. Заголовок запроса `Watchbane-Search-Outcome: 1` включает поле `outcome` с фиксированными кодами `state` и `reason`. Сервер подтверждает эту версию тем же заголовком только при успешном ответе. Неизвестная или повторённая версия возвращает 400; наличие поля без явно подтверждённой версии не считается новым протоколом. Для обоих вариантов действует `Cache-Control: no-store`; ответ варьируется по этому заголовку.

`candidates` обозначает варианты из индекса, не уверенное попадание. `clarification` означает, что исключение пока не поддерживается, не хватает сюжетных деталей или подходящих записей в текущем каталоге. `scope_refusal` используется только там, где существующая проверка уже отказывалась от запроса вне темы. Ранжирование, пределы индекса и эвристика распознавания не изменились. Новый протокол не заводит журнал причин, запросов или истории согласий.

Для проверки подписей в Qt добавьте к настройке порта `WATCHBANE_EXPERIMENTAL_STORY_OUTCOME=1`. Прежний сервер поддерживается при выключенном флаге. При включённом флаге Qt требует подтверждение версии и распознаваемое состояние; при несовместимости показывает ошибку, не отправляет запрос повторно и не запускает локальный поиск без действия пользователя.

### Переход на новую версию каталога

Если матрица для предыдущего разрешённого снимка уже проверена и есть в том же серверном кэше, можно явно добавить `--previous-catalog /path/to/previous-approved.jsonl` вместе с `--cache-dir`. При совпадении модели и обработки переиспользуются только строки с тем же типизированным ID и точным описанием. При попадании по текущей версии старый JSONL даже не читается; отсутствующий или непригодный предыдущий источник не мешает обычному пересчёту. Сервер не меняет входные каталоги и старую матрицу. Автоматической ротации и поиска «последней» версии нет.

Для сравнения способов получения переводов `tools.qa.compare_tmdb_translation_fixtures.compare_translation_fixtures` принимает парные тела с одинаковым набором типизированных ID и отдельным равным лимитом симуляции для каждой стратегии. Отчёт выводит только счётчики запуска, суммарный размер и p95, размеченные локали и отдельные пропуски. Разметка провайдера и запрошенная локаль учитываются раздельно. Это офлайн-расчёт, не замер действующей квоты TMDb и не включение сетевого маршрута.

### Память: холодное построение и перезапуск с готовыми векторами

### Решение по хостингу без расходов

- [Hugging Face Spaces](https://huggingface.co/docs/hub/spaces-overview): CPU Basic не тарифицируется по часам, но создание Docker Space требует платного плана. Бесплатное исключение для личного Gradio/ZeroGPU не подтверждает бесплатное развёртывание нашего FastAPI.
- [Koyeb](https://www.koyeb.com/docs/reference/instances) и [Railway](https://docs.railway.com/pricing/plans): бесплатная память около 512 МБ, меньше измеренной RSS даже с готовым кэшем. [Google Cloud Free Tier](https://docs.cloud.google.com/free/docs/free-cloud-features) требует активного биллинга; [отсечка расходов Google Cloud](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps) не мгновенная, превышение оплачивается.
- Oracle A1 остаётся условным кандидатом, не выбранным хостингом. Нативная CI-проверка ниже подтверждает бюджет одного серверного процесса, не работу всего сервиса с прокси и каталогом. Публично не развёрнуто.

### Бюджет одного процесса и перегрузка на нативном ARM64

[CI-прогон на точном SHA](https://github.com/veitnemed/watchbane/actions/runs/45019378017/job/137198658135): 1 000 синтетических плотных описаний, FP32 E5, Linux ARM64, два свежих контейнера, каждый с 2 CPU, 2 ГиБ и без swap. При холодной сборке процесс готов через 150,82 с; после запуска с разрешённой только для чтения матрицей через 5,49 с. Первый ответ после готовности при попадании в кэш занял 0,76 с, его не следует путать с медианой 21 тёплого запроса (38,31 мс). Пики cgroup 1,14 и 1,04 ГиБ. Нет OOM или событий достижения лимита; порядок типизированного Top-5 совпал на всех семи запросах.

После перезапуска три серии из шести одновременных клиентов дали по одному 200 и пяти `503 search_busy` с `Retry-After: 1`. Выдача принятых запросов совпала с последовательной. Последующий запрос прошёл после каждой серии (макс. 38 мс). Это контролируемый отказ и восстановление, не шесть параллельных вычислений, не отдельный лимит по пользователю и не публичная нагрузочная приёмка. Синтетический каталог не доказывает покрытие или качество на реальном TMDb.

### Меньшие пакеты построения E5 (эксперимент)

При ограниченном окружении сервер можно запустить с `--startup-passage-batch-size 4`. Допустимы значения 1–16; умолчание 16 не изменилось. Размер влияет только на вычисление векторов описаний при запуске, не на кодирование запросов и подсказок. Для каждого нестандартного размера отдельное пространство кэша, в том числе при чтении предыдущего снимка; старый кэш не перезаписывается.

На том же малом наборе (50 записей, x86-64, две логические CPU) размер 4 при лимите адресного пространства 2 ГиБ дал первый холодный запуск за 4,91 с с пиковой RSS 977 МиБ; перезапуск с его кэшем занял 2,48 с, пик 889 МиБ. Контрольный холодный запуск размером 16 под 3 ГиБ в этой серии занял 12,95 с, пик 1450 МиБ. Это одиночные замеры, а не сравнение гарантированных задержек. На 10 одинаковых русских запросах полные JSON-ответы и порядок ID совпали с контрольным режимом, после перезапуска ответы не изменились. Старый файл матрицы побайтно не изменился. Это проверка совместимости на малом каталоге, не вывод о качестве на всей базе и не приёмка хостинга.

### Приёмка будущего приближённого индекса (ANN)

**Сейчас:** даже подготовленный режим делает точный плотный поиск. Не заменяйте его приближённым только по замеру скорости или совпадению списков кандидатов. При слиянии RRF (по порядковым местам) текущий поиск берёт объединение двух top-40, но учитывает места обоих каналов среди всех подходящих записей. Например, нулевое лексическое место и плотное место 40 дают `1/100 + 0.35/60 ≈ 0.01583`, обгоняя запись только с плотным местом 5 (`1/65 ≈ 0.01538`). При потере плотного вклада первая оценка становится `0.00583`. Точное пересчитывание расстояний только для объединения кандидатов не восстанавливает утерянные глобальные места. Если алгоритм использует места внутри ограниченного списка, это новая схема ранжирования, а не эквивалентная оптимизация.

[Pgvector: фильтрация](https://github.com/pgvector/pgvector#filtering) выполняется после приближённого скана, поэтому узкая выборка может вернуть меньше элементов. [Итеративный скан](https://github.com/pgvector/pgvector#iterative-index-scans) (pgvector ≥ 0.8.0) расширяет область поиска до заданного лимита, но не гарантирует полного покрытия. Сравнить точный поиск по избирательной выборке с ANN и итеративным сканом; не расширять фильтр пользователя для наполнения результатов.

На одном разрешённом каталоге и замороженных запросах сопоставлять отдельно:

1. Долю возвращённых точных плотных кандидатов (знаменатель — `min(40, число допустимых записей)`, пустые выборки отдельно), команды фильтрации «фильм», «сериал», «тип и год», число недоборов и ошибочных типов/лет. Сравнивать типизированные TMDb ID, а не названия или числа ID.
2. Итоговую выдачу: совпадение первым результатом и упорядоченной пятёркой с точным режимом отдельно от доли верных целей в top-1/5; ошибки на запросах без цели и на выборках, где отсутствует целевой тайтл, считать отдельно. Режим с заявленной эквивалентностью не должен менять выдачу. Для новой формулы заранее определить допустимые потери по каждой группе, включая узкие фильтры.
3. p50/p95 и пиковую память всего процесса при одинаковой модели, снимке, фильтрах и нагрузке. Отдельно фиксировать время точного запасного пути, если он используется. Большее число возвращённых строк не доказывает больший recall.

Пока нет замеров ANN на разрешённом крупном каталоге, не включать его по умолчанию. Синтетические проверки фиксируют контракт ранжирования, не подтверждают качество pgvector или PostgreSQL. Не публиковать исходные описания или приватные оценочные запросы.

Базовая проверка до ANN: на одном серверном снимке из 50 реальных тайтлов, Linux x86-64 и FP32 E5 обычный и подготовленный точные режимы вернули одинаковые полные HTTP JSON-ответы для всех 156 замороженных запросов, включая 30 посторонних и 6 с недостаточными деталями. Это только проверка совпадения двух реализаций. Даже потенциально неверные ответы могли совпасть; цели без подтверждённого ID в оценку релевантности не включаются. Отдельная синтетическая регрессия проверяет итоговый top-5 на границе 39/40 и узкий фильтр типа и года, в котором глобальные лидеры не проходят фильтр.

### Репетиция смены каталога без остановки поиска

`/healthz` подтверждает готовность процесса, а не версию его индекса. Лабораторная команда запускает две отдельные локальные копии API, сверяет SHA-256 обоих снимков и проверяет через поиск типизированный ID, отсутствующий в старом снимке и находящийся в новом. Перед переключением новая копия должна быть готова и вернуть маркер. Отдельная попытка с испорченным JSONL должна завершиться ошибкой, оставив старый процесс доступным.

```sh
python -m tools.qa.exercise_story_handover \
  --old-catalog /path/to/approved-old.jsonl --old-sha256 OLD_SHA256 \
  --new-catalog /path/to/approved-new.jsonl --new-sha256 NEW_SHA256 \
  --model-dir /path/to/verified-e5 --query-file /path/to/diagnostic.txt \
  --marker-id tmdb:movie:137 --samples 8
```

Подставьте свои SHA-256 и ID для конкретной пары. Файл содержит один диагностический сюжет, для которого маркер ожидается в первых десяти результатах нового снимка. Команда выводит агрегированные замеры, не сами запросы и карточки. Она не запускает прокси, не меняет публичные маршруты и не выполняет автоматическую ротацию: переключение делает один последовательный тестовый клиент.

Отдельный прогон на Linux x86-64, 49 → 50 разрешённых записей и той же FP32 E5, использовал переиспользование матрицы и лимит адресного пространства 2 ГиБ **на каждый процесс**, с общей привязкой к двум логическим CPU. Новая копия стала доступной за 2,37 с. При запуске новой копии 19 из 19 проб к старой прошли (p95 53 мс); после переключения 8 из 8 проб к новой прошли (p95 19 мс, после отдельной первой проверки). Пять проб к старой при возврате и пять к новой при повторном переключении тоже прошли; повреждённая копия не стала готовой. Это последовательные пробы, а не гарантия отсутствия потерь при параллельных запросах.

В 38 выборках двух процессов максимум суммы RSS составил 1825 МиБ, суммы PSS — 1794 МиБ. Это наблюдения из Linux `/proc`, не точный пик, не общий лимит памяти контейнера и не оценка всего развёртывания с прокси или БД. Для внешнего сервиса остаются обязательны нагрузка с запросами в полёте, развёртывание в реальном лимите cgroup, проверка отката маршрута и разрешение на использование данных.

Сама команда также проверена с двумя полными построениями (без матричного кэша) при тех же ограничениях: новая копия готова за 4,99 с, 28 из 28 направленных проб прошли, включая отказ от staging-версии, возврат к старой и повторный выбор новой. p95 восьми проб к старой во время подготовки составил 35 мс; p95 восьми проб после переключения — 29 мс. При восьми измерениях p95 фактически равен максимуму; это не производственный SLO.
